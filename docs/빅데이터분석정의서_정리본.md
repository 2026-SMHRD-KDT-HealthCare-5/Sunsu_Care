# 빅데이터 분석 정의서 — Sun手Care

> 주제: YOLO 기반 선케어 제품 이미지 분석 및 맞춤형 추천 서비스
> ※ 기존 정의서 항목 구조에 맞춰, VS Code 코드베이스에서 확인된 내용만 작성.

---

## 1. 개요

**1) 아이디어 주제**
YOLO 기반 선케어 제품 이미지 분석 및 맞춤형 추천 서비스 (Sun手Care)

**2) 개발 목표**
YOLOv8 객체 탐지와 CLOVA OCR로 선크림 라벨의 전성분을 추출하고, 사용자의 피부 타입·활동 환경·기피 성분에 맞춰 0~100점 적합도 점수와 Gemini AI 추천 이유를 제공한다.

**3) 개발 내용**
- 설문(피부 타입·활동 환경·선호 제형·기피 성분) 기반 적합 제품 추천 (TOP 3)
- 성분표 촬영/업로드 → OCR 추출 → 피부 적합도 평가 및 핵심·주의 성분 분류
- Gemini LLM 기반 개인 맞춤 자연어 추천 이유 생성

---

## 2. 기능별 빅데이터 분석 명세서

**기능명**: OCR 기반 선크림 성분 분석 및 피부 타입·니즈 기반 적합도 평가/제품 추천

### 데이터 준비

**데이터 정의**
MySQL 8개 테이블로 구성 (`README.md`)
- 성분 사전 `tb_ingredient` : 성분명 `ingre_name`, EWG 등급 `ewg_grade`, 효능·주의 설명 `skin_warning`
- 제품 마스터 `tb_product` : `prod_name`, `brand_name`, `spf_val`, `pa_val`, `uv_type`, `image_filename`
- 제품-성분 매핑 `tb_product_detail`
- 사용자 프로필 `tb_profile` : `skin_type`, `activity_env`, `prod_type`, `avoid_ingredient`
- 업로드/분석 `tb_upload`, `tb_analysis`, `tb_analysis_log`

**데이터 획득 방법**
- 성분·제품 데이터를 MySQL DB(`tb_ingredient`, `tb_product`)에 적재하여 활용
- 핵심 효능 성분의 `skin_warning` 컬럼은 키워드 기반 SQL로 일괄 시드
  (`update_ingredient_warnings.sql` — '도움'/'기능성' 포함 = 핵심 성분 판정 기준)
- 분석 대상 이미지는 사용자가 카메라 촬영 또는 파일 업로드로 입력

**수집 데이터**
- 성분 사전 약 7,000개 (`ingre_name`, `ewg_grade` 1~10, `skin_warning`)
- 제품 마스터 약 300개 (브랜드·SPF/PA·자차 타입 포함)
- 사용자 프로필(피부 타입·활동 환경·선호 제형·기피 성분)

### 전처리

**전처리 과정**
- OCR 텍스트 정규화: 한글·영문·숫자 외 노이즈/공백 제거 (`clean_text()`, `ingredient_matcher.py`)
- 이미지 전처리: RGBA→RGB 변환 후 numpy 배열화 (`ocr_service.preprocess_image_bytes`)
- OCR 업로드 최적화: JPEG quality 70 + optimize 압축 (`ocr_service.request_full_image_ocr`)
- 매칭 최적화: 길이 인덱스(질의어 길이 50~200% 후보만 비교), 중복 질의·성분 제거, EWG↑·이름순 결정론적 정렬

**전처리 데이터**
- 정제된 성분 사전 약 7,000개 (EWG 등급·효능 설명 포함)
- 매칭 후보군: 길이 인덱스로 7,000개를 질의별 평균 수백~1,000개 수준으로 축소

### 데이터 분석

**데이터 분석 목표**
① 피부 타입·니즈 기반 적합 제품 추천(TOP 3)
② 업로드 성분표를 OCR 분석하여 적합도(0~100점) 평가 (성분 매칭 기반 정보 제공, 의학적 진단 아님)

**데이터 분석 시나리오** — 입력·처리가 달라 2개 경로로 분리, 채점 엔진만 공유

| 구분 | 경로 A — 설문 후 추천 | 경로 B — 성분표 스캔 평가 |
|---|---|---|
| 입력 | 프로필(설문)만 | 제품 사진 |
| OCR/YOLO | 미사용 | 핵심 단계 |
| 분석 대상 | `tb_product` 전 제품 | 검출된 제품 1개 |
| 출력 | 추천 제품 TOP 3 | 적합도 점수 + 성분 분류 |
| 코드 위치 | `getRecommendationsHandler` | `pipeline.py` → `callbackHandler` |

- 경로 A: 설문 수집 → 전 제품에 적합도 산출 → 점수 내림차순 상위 3개 추천
- 경로 B: 이미지 업로드 → YOLOv8 라벨 검출 + CLOVA OCR(병렬) → 정규화 후 성분 DB 매칭(직매칭 + RapidFuzz, cutoff 80) → 적합도·핵심·주의 성분 분류 → Gemini 추천 이유 생성

**데이터 분석 결과** — 적합도 산출 규칙 (`compatibilityScore.js`)
- BASE 70점에서 시작
- EWG 위험 감점 (등급 7+: −20 / 5+: −10 / 3+: −5)
- 핵심 성분 가점 ('도움'·'기능성' 포함, +3, 최대 +15)
- 기피 성분 매칭 감점 (−25)
- 피부 타입 보정 (민감성 추가 감점 / 건성 보습 성분 가점 / 지성 오일 성분 감점)
- 활동 환경 보정 (야외 시 자외선 차단 성분 가점)
- 0~100점 클램프, 상태: 최적(90+) / 적합(75+) / 주의(50+) / 부적합(<50)

### 모델 생성 및 학습

**모델링 목표**
① 성분표 이미지에서 OCR로 성분 텍스트 추출
② 성분-프로필 매칭으로 적합도 산출 및 적합 제품 추천

**학습 모델**
- 성분표 영역 검출: YOLOv8 (Ultralytics, 학습 가중치 `best.pt`)
- 텍스트 인식: 네이버 CLOVA OCR API (한글·영문, 외부 API)
- 성분명 매칭: 직매칭 + RapidFuzz Fuzzy (`partial_ratio`, 길이 인덱스, score_cutoff 80)
- 적합도 산출: 룰 기반 가중치 알고리즘 (학습 불필요)
- 추천 이유: Google Gemini Flash LLM (멀티모델 폴백 + 파일 영속 캐시)

**학습 방법**
- YOLOv8: `best.pt` 로드, 단일 클래스 'SP'(성분표) 매핑, 신뢰도 임계값 conf=0.6 (`test_yolo_detection.py`)
- 성분 매칭: 질의어 길이 50~200% 후보만 비교, 중복 제거, EWG↑·이름순 결정론적 정렬 (`ingredient_matcher.py`)
- Gemini: 피부과 전문의 페르소나 프롬프트(2~3문장·200자·마크다운 금지), temperature 0.85 / maxOutputTokens 1500 / topP 0.95 / topK 40
- Gemini 폴백 체인: `2.5-flash → 2.0-flash → 2.5-flash-lite → 2.0-flash-lite`, 429 시 모델별 cooldown 후 다음 모델 우회
- 추천 이유 캐시: 파일 영속(`ai_reason_cache.json`), LRU 최대 500개

**모델 예측 결과** (`pipeline.py` 시간 측정 / `README.md` 성능표)

| 단계 | 처리 내용 | 결과 |
|---|---|---|
| 이미지 업로드 | Canvas 1024px 리사이즈 + JPEG 압축 | 5~10MB → 약 500KB |
| OCR + YOLO 병렬 | CLOVA 인식 + YOLO 검출 동시 실행 | 순차 대비 단축 |
| 성분 매칭 | 약 663 segment × 7,000 성분(≈460만 비교) | 4.3초 → 0.3초 |
| Gemini 캐시 hit | 파일 영속 캐시 재사용 | 약 50ms |
| 분석 1회 총합 | 업로드~결과 | 20~25초 → 5~7초 |

산출물: YOLOv8 바운딩 박스 / CLOVA 텍스트 필드 배열 / RapidFuzz 검출 성분 객체 배열 / 적합도 0~100점 + 감가점 내역 / Gemini 추천 이유 텍스트

### 검증

**분석 검증 방안** (코드에 실제 구현된 검증 장치)
1. 결과 일관성(결정론) — 정렬·중복 제거로 같은 입력 → 항상 같은 검출 성분·동일 점수
2. 중복 분석 방지 — 검출 성분명 fingerprint 비교로 중복 저장 차단 (`callbackHandler`)
3. 점수 재계산 동기화 — 히스토리 조회 시 재채점, DB 값과 다르면 자동 UPDATE (`getAnalysesHandler`)
4. 최신 성분 정보 반영 — 조회 시 `tb_ingredient` 일괄 조회로 최신 `ewg_grade`/`skin_warning` 덮어쓰기
5. LLM 안정성·비용 — Gemini 429 시 4개 모델 자동 우회, 캐시 hit 시 호출 0회
6. 히스토리 관리 — 사용자별 최대 5건 유지, 초과 시 가장 오래된 항목 자동 삭제 (`saveAnalysisHandler`)

| 이미지 업로드 크기 | 5~10MB → 약 500KB |
